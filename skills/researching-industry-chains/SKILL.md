# 产业链来源检索与解析

## 任务目标

按 Runner 中的正式主题寻找独立、高质量、全国范围的产业链来源，忠实还原来源实际表达的节点结构和企业归属，并通过 `industry-chain` CLI 写入固定九字段数据。

本任务不是总结行业知识，也不是建立“更合理”的标准产业链。模型上下文只作为**当前来源的临时工作区**；已经完成的来源以 Runner 中的持久化结果为准。

## 必需输入与能力

运行前必须具备：

- Runner 中的正式主题、`path`、`aliases` 和 `node_id`；
- 互联网搜索能力；
- 网页和 PDF 浏览、翻页、缩放或高分辨率渲染能力；
- 实际视觉读图能力；
- 可调用的 `industry-chain` CLI。

缺少影响网页/PDF查看、视觉判断或 CLI 写入的关键能力时，不得用 OCR、正文或常识猜测代替；领取主题后发现能力不可用，提交失败状态。

## 业务不变量

本任务始终遵守以下规则：

1. 一个网页、报告或 PDF 独立形成一个来源组，不跨底层文档拼接节点或企业。
2. 来源展示的每个可读节点都必须处理，包括父节点和无企业节点。
3. 来源发现的每个可读企业或企业组都必须处理：挂到直接证据支持的最小节点，或明确记为无法归属。
4. 不用行业常识补节点、改节点名称、重排来源结构或猜企业归属。
5. 一个来源解析完成后立即写入 Runner，不等待其它来源。
6. CSV/XLSX 是来源事实的投影，不是 Agent 对产业链的重新整理。

在以下时点重新检查这一节：领取新主题后、开始一个新来源前、准备生成 `records` 前、准备提交主题终态前。无需反复全文重读 Skill。

## 来源准入规则

候选来源只有依次通过以下门槛，才进入深度解析。

### 1. 地域范围

除非正式主题自身明确要求地方范围，否则默认只接受研究对象为**全国、中国整体或全国市场**的来源。

默认排除：

- 省、市、区县级产业链；
- 园区、开发区产业链；
- 地方产业集群、招商图谱、地方重点企业分布。

判断的是**来源研究对象**，不是发布机构所在地。深圳研究机构发布的《中国机器人产业链》可以保留；国家级机构发布的《北京市机器人产业链》仍应排除。

产业覆盖可以比正式主题更宽或只覆盖其中一个阶段，但地域范围不得以“范围变化”备注放宽。非地域性的产业边界变化可以保留，并在来源首行备注具体差异。

### 2. 来源质量

优先顺序：

1. 政府部门和政府研究机构、全国性行业协会、证券公司研究所、权威科研机构和研究院；
2. 头部咨询机构、专业行业研究机构、正式行业白皮书、上市公司或产业龙头的正式产业研究材料；
3. 专业产业数据库、专业财经媒体的深度原创研究、垂直行业媒体的原创深度内容、大学或实验室产业研究材料。

普通新闻、聚合、营销、自媒体和低专业度转载默认跳过，例如普通腾讯新闻/搜狐/网易/今日头条/百家号页面、个人博客、营销软文、新闻聚合页和只摘录研报结论的资讯页。

发现转载时优先追溯原始报告或原发布页。原始来源不可访问、而转载完整保留产业链证据时，才使用转载页。

优先采用 2024 年及以后来源；较早来源在首行备注“来源早于2024年”，日期无法确认时写“发布日期未识别”。

### 3. 产业链资格

来源必须同时满足：

1. 图、表或正文明确表达产业角色之间的连续关系，例如原材料/零部件 → 制造/服务 → 集成/运营 → 应用/客户，能够回答“谁提供什么给谁”；
2. 至少一组企业能够通过同一来源内部证据直接对应一个已有节点。

标题含“产业链”“全链路”“生态图谱”，或图中存在方框、箭头，本身不能证明产业链资格。

以下内容单独出现时不合格：

- 工艺流程、业务流程、工作流和工作原理；
- 技术路线、系统架构和功能模块图；
- 产品结构、零部件清单和应用场景集合；
- 企业名单、相关标的表、排行榜、展商目录、区域热力图和没有产业角色关系的生态版图。

未通过任一来源准入门槛时立即跳过，不进入反复截图、读图和深度解析。

## 单个主题执行流程

### 1. 确认主题

领取结果中的正式主题、`path` 和 `aliases` 是主题身份依据。`path` 只用于理解目录位置，不作为产业链节点。

搜索词覆盖正式主题、批准别名和必要的相关表达，可组合“产业链、产业图谱、全景图、研究报告、企业布局、竞争格局”等限定词。

### 2. 搜索候选来源

搜索阶段可以一次发现多个候选 URL，但只做候选发现和快速筛选，不把多个来源同时放入深度解析上下文。

对每个候选按固定顺序判断：

1. 是否属于全国范围；
2. 来源主体和内容是否足够专业；
3. 是否存在更优的原始来源；
4. 是否具备产业链资格。

明显不合格时立即跳过。

**禁止先打开很多文章全部读完，再统一解析和写入。**

### 3. 一次只处理一个来源

任何时候只允许存在一个“已经开始深度解析但尚未写入 Runner”的来源。

一旦开始完整阅读某个来源，在该来源完成解析、覆盖检查并成功写入 Runner 前，不得开始第二个来源的深度解析。

单来源事务固定按以下顺序执行：

```text
完整扫描来源
→ 来源清单
→ 节点清单
→ 企业清单
→ 还原节点树和企业归属
→ 生成九字段 records
→ 节点覆盖检查
→ 企业覆盖检查
→ 立即 dataset insert
→ 确认写入成功
→ 当前来源事务结束
```

### 4. 完整扫描当前来源

同一底层文档的正文、网页分页、主产业链图、补充节点图、后续企业图表和明确正文可以综合；其他 URL 或其他报告的内容不得补入。

网页出现页码、`下一页` 或类似分页入口时，确认总页数并扫描到最后一页。长篇 PDF 可以用目录、图表目录和文本搜索定位候选页，但用于节点或企业判断的图片页必须实际查看。

在当前上下文维护一份简短的**来源清单**，逐项登记：

- 页码、分页或图表位置；
- 类型：主产业链图、补充节点图、企业图表、明确正文、排除项；
- 是否已查看；
- 是否提供节点；
- 是否提供企业关系。

对实际用于还原产业链结构的主产业链图，同时记录可供人回看的位置说明，供来源组首行 `备注` 使用。

来源清单只回答“当前来源是否已经读完”，不写入 Runner。

### 5. 视觉读取：清楚即停止

先看完整页面或完整图。

如果已经能够可靠读取节点文字、层级/连接关系、企业名称以及企业与节点的直接关系，立即进入解析，不再为了“更保险”重复截图、重复放大、OCR、下载原图或再次验证同一区域。

只有存在具体不可读内容时，才处理对应局部，例如：

- 某个节点文字看不清；
- 某条连接关系不清；
- 某组企业名过小；
- 表头和企业的对应关系不清。

此时只对必要局部裁切、放大或高分辨率渲染。OCR 只能辅助识字，不能替代视觉结构判断。

原则：

```text
清楚 → 解析
不清楚 → 只处理不清楚的局部
```

主产业链图整体无法可靠读取，且正文不能独立、明确地给出完整产业链结构和企业关系时，排除该来源，不提交残缺主图。

### 6. 建立节点清单

来源扫描结束后，先在当前上下文列出所有可读节点的完整路径，再生成 `records`。

例如：

```text
上游
上游 > 核心零部件
上游 > 核心零部件 > 丝杠
上游 > 核心零部件 > 减速器
```

每个节点只有“已投影”或“尚未投影”两种状态。存在尚未投影节点时，不得写入来源组。

还原节点时：

- 以来源中的框、分组标题、连接线、缩进、包含关系和阅读方向为准；
- 图片或表格优先，正文中“包括、分为、由……构成”等明确枚举可补充结构；
- 父节点本身也是节点，无论是否有企业都保留；
- 子节点不能用父节点替代，并列节点分别成行；
- 无企业节点仍保留，公司留空；
- 一个框表达组合节点时原样保留；表达多个并列节点时拆开；
- 省略号、示意占位符和装饰文字不生成节点；
- 节点名称、层级和顺序保持来源原义，不标准化、不润色、不补全。

分类 1 至分类 4 必须连续；超过四级时，从第四级开始按原始顺序合并为 `第四级 > 第五级 > 第六级`，并在来源首行备注说明。

### 7. 建立企业清单并挂载企业

对当前来源中每个可读企业或企业组，在上下文中记录：

- 企业或企业组原文；
- 直接证据对应的节点；
- 状态：`已挂载` 或 `无法归属`。

不存在“读到了但没处理”的第三种状态。

企业归属证据按以下顺序判断：

1. 产业链图中的位置、连接、框或图例；
2. 企业表的标题、分组和字段；
3. 正文明示某企业生产、提供、运营或布局某个节点对应的产品或服务。

使用离企业名单最近的明确节点标题、表头或语义分组作为归属锚点。分号、分组标题或表格行已经区分企业组时，不得把相邻企业组合并到更宽的父节点。

“主要上市公司、相关企业、代表公司、相关标的”等名单不能仅凭主题相关性挂载；只有同一来源另有明确节点关系时才使用。

企业只写在直接证据支持的最小节点行：

- 证据只到父节点时只挂父节点，不向子节点继承；
- 同一路径企业合并到一行，完全重复名称删除；
- 按来源出现顺序用顿号连接；
- 证据冲突时依次采用图中明确位置、分组表/企业列表、正文明确介绍；
- 无法消解时不强行挂载；
- 优先使用来源内部确认的企业全称，只能确认品牌或简称时保留原样；
- 不用外部知识扩展、改写或推断。

无法确认归属的企业不写入公司字段，并在来源首行备注中写明“发现但无法归属：企业名称”。

### 8. 生成九字段 records

只在当前来源完成节点清单和企业清单后生成固定九字段，不增加证据、置信度、搜索过程、截图或推理字段：

```json
{"records":[{
  "主题":"正式主题",
  "信源主体":"发布主体",
  "分类1":"上游",
  "分类2":"节点",
  "分类3":"",
  "分类4":"",
  "公司":"甲公司、乙公司",
  "信源URL":"https://example.com/report",
  "备注":"产业链图位置：第 12 页，图 3《XX产业链》"
}]}
```

一行表示“从根节点到当前节点的完整路径”以及直接归属于路径终点的企业集合，不是一家企业一行，也不能把整棵产业链压成一行。

九个字段全部是字符串。主题、信源主体、分类 1 和信源 URL 不能为空；分类不能断层；组内主题、信源主体和 URL 必须一致；只有第一行填写备注；来源组至少一行公司非空；信源 URL 必须是合法 HTTP(S) 地址。

来源组第一行 `备注` 必须包含**产业链图位置说明**，让人工可以回到原来源快速找到用于还原结构的产业链图：

- PDF / 报告：优先写页码，并补充图号或图题，例如 `产业链图位置：第 12 页，图 3《XX产业链》`；
- 网页：写可稳定定位的正文小节、图题或图片顺序，例如 `产业链图位置：正文“产业链结构”小节，第 2 张图《XX产业链》`；
- 使用多张产业链图共同还原结构时，把实际使用的图位置全部列出；
- 合格来源没有产业链图，而是由表格或明确正文直接给出产业链结构时，不编造图片位置，写 `产业链图位置：无（结构来源：表格/正文，位置：具体页码或小节）`。

其它备注信息继续写在同一首行备注中，与产业链图位置用 `；` 分隔，例如范围变化、发布日期、层级合并和无法归属企业。

来源组按原图或原文阅读顺序排列，父节点行放在其子节点之前。

信源主体按发布关系填写：

- 原始发布：`原始主体`；
- 转载或托管：`发布平台（原始主体）`；
- 只能识别发布平台：`发布平台（原始主体未明）`。

### 9. 完成前覆盖检查

写入前只做当前来源的完整性检查，不重新寻找其它文章验证本来源。

**节点覆盖：**

```text
来源节点 - 已投影节点 = ∅
```

节点清单中的每个可读节点都必须能在 `records` 中找到对应完整路径。

**企业覆盖：**

```text
来源企业 -（已挂载企业 + 无法归属企业）= ∅
```

以下任一情况都表示当前来源尚未完成：

- 读到企业，但既没有进入公司字段，也没有记为无法归属；
- 只解析主图企业，忽略同一来源后续企业图表；
- 因企业数量多而抽样、概括或用“等”代替明确可读名单；
- 只保留与搜索关键词最接近的一部分企业；
- 父节点或无企业节点被省略；
- 并列节点被合并；
- 父节点企业被继承给子节点。

覆盖未完成时继续处理当前来源，不打开下一篇来源，不调用 `dataset insert`。

### 10. 立即写入当前来源

当前来源同时通过节点覆盖和企业覆盖后，立即一次性写入：

```powershell
$OutputEncoding = [System.Text.UTF8Encoding]::new($false)
$env:PYTHONIOENCODING = 'utf-8'
$payload = @'
{"records":[{"主题":"正式主题","信源主体":"发布主体","分类1":"上游","分类2":"节点","分类3":"","分类4":"","公司":"企业名称","信源URL":"https://example.com/report","备注":"产业链图位置：第 12 页，图 3《XX产业链》"}]}
'@
$payload | industry-chain dataset insert --runner-id <runner_id> --scope source_group --parent-id <node_id> --claim-token <claim_token> --input -
```

**写入成功是当前来源事务的结束门槛。**

禁止：

```text
来源 A 解析完
来源 B 解析完
来源 C 解析完
最后统一写入
```

必须：

```text
A → insert 成功
B → insert 成功
C → insert 成功
```

写入成功后，后续工作以 Runner 中已持久化的数据为准。当前来源的来源清单、节点清单、企业清单和详细内容不再作为后续来源的工作上下文，只保留必要的来源去重信息和主题进度。

需要纠正已写入数据时，先用 `dataset get` 查看，再用 `dataset patch`、`dataset replace` 或 `dataset remove` 精确修改。XLSX 是交付投影，Runner JSON 是事实源。

### 11. 继续搜索与主题终态

每写入一个来源后再继续搜索或处理下一个候选来源，不设置固定来源数量。

一个完整搜索轮次覆盖正式主题、批准别名和相关表达，并组合产业链、产业图谱、全景图、研究报告、企业布局、竞争格局等限定词。第二轮改变查询组合或来源入口，并按底层文档去重。

连续两轮没有新增独立合格来源后，才算搜索饱和。

准备提交终态前重新检查“业务不变量”，然后：

```text
industry-chain topic finish --runner-id <runner_id> --node-id <node_id> --claim-token <claim_token> --outcome completed
industry-chain topic finish --runner-id <runner_id> --node-id <node_id> --claim-token <claim_token> --outcome no_qualified_source
industry-chain topic fail --runner-id <runner_id> --node-id <node_id> --claim-token <claim_token> --code <错误代码> --message <简短说明>
```

`completed` 要求至少一个来源组；`no_qualified_source` 要求没有来源组。浏览器、网络、视觉能力或运行环境出现系统性异常时提交失败，不把异常主题视为完成。

## 最小示例

### 父节点和并列子节点

来源：

```text
核心零部件
├─ 丝杠
├─ 减速器
└─ 传感器
```

必须保留四条路径：

```text
核心零部件
核心零部件 > 丝杠
核心零部件 > 减速器
核心零部件 > 传感器
```

### 企业证据只到父节点

来源：

```text
核心零部件：甲公司、乙公司
├─ 丝杠
└─ 减速器
```

正确投影：

```text
核心零部件          公司=甲公司、乙公司
核心零部件 > 丝杠   公司=

```

不得把甲公司、乙公司复制或猜分到子节点。

## Runner 与租约

所有 Runner 命令显式传入 `--runner-id`：

```text
industry-chain runner create --name <任务名称> --config <topic_identity.yaml路径>
industry-chain runner status --runner-id <runner_id>
industry-chain topic claim-next --runner-id <runner_id>
industry-chain topic claim --runner-id <runner_id> --node-id <node_id>
industry-chain topic claim --runner-id <runner_id> --node-id <node_id> --reopen
```

保存领取响应中的 `claim_token` 和 `lease_expires_at`。主题处于 `in_progress` 时，数据写入、修改、替换、删除、续租、完成和失败都携带当前有效令牌。

长时间处理至少每 20 分钟续租一次：

```text
industry-chain topic renew --runner-id <runner_id> --node-id <node_id> --claim-token <claim_token>
```

不要创建中间 JSON；截图、PDF、网页下载物、OCR 文件和日志只用于当前判断，不写入 Runner。Runner 目录只保留 `runner.json` 和交付 XLSX。

## SubAgent 派发模板

每个 SubAgent 只处理互不重叠的 `node_id` 范围，不预设来源、节点或企业：

```text
你负责 Runner {{runner_id}} 的 node_id {{node_id 或范围}}。先阅读 skills/researching-industry-chains/SKILL.md，领取或确认主题并保存有效 claim_token。

严格按 Skill 的来源准入和单来源事务执行：默认只收全国范围和专业来源；一次只深度处理一个来源；图片已经清楚时停止额外验证；当前来源完整还原节点和企业、通过覆盖检查后立即通过 industry-chain CLI 写入，再处理下一来源。

所有数据操作和终态操作携带有效 claim_token。搜索饱和后提交 completed、no_qualified_source 或 fail，并汇报 node_id、正式主题、终态、来源组数、数据行数、来源 URL 和交付 XLSX 路径。
```

主题终态后汇报 `node_id`、正式主题、终态、来源组数量、数据行数、来源 URL 和交付 XLSX 路径；失败时补充原因。
