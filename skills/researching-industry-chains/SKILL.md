# 产业链来源检索与解析

## 适用条件

用于按正式主题寻找独立来源，还原来源实际表达的产业链节点和企业归属，并写入 Runner。运行环境必须具备互联网搜索、网页和 PDF 浏览、截图或高分辨率渲染、实际视觉读图以及 `industry-chain` CLI 能力。缺少任一关键能力时，不得用正文、OCR 或常识猜图；领取主题后发现能力不可用，提交失败状态。

## 四个终态门槛

来源组写入前必须同时满足：

1. **产业链资格**：来源表达了不同产业角色之间的供给、生产或服务、集成或运营、应用或需求关系，能够回答“谁提供什么给谁”。
2. **来源完整**：网页全部分页和报告相关页已经扫描到末尾，已发现的产业链图、企业图表和明确正文都已处理。
3. **节点完整**：每个可读节点都有一条从根节点到该节点的完整路径行，父节点和无企业节点也不省略。
4. **企业可核对**：每个可读企业组都已挂到直接证据支持的最小节点，或明确记为无法归属；不得静默丢失企业，也不得猜测挂载。

任一门槛未通过，不得写入该来源组或提交主题完成。

## Runner 与租约

所有 Runner 命令都显式传入 `--runner-id`。

```text
industry-chain runner create --name <任务名称> --config <topic_identity.yaml路径>
industry-chain runner status --runner-id <runner_id>
industry-chain topic claim-next --runner-id <runner_id>
industry-chain topic claim --runner-id <runner_id> --node-id <node_id>
industry-chain topic claim --runner-id <runner_id> --node-id <node_id> --reopen
```

保存领取响应中的 `claim_token` 和 `lease_expires_at`。主题处于 `in_progress` 时，数据写入、修改、替换、删除、续租、完成和失败都携带当前有效令牌。长时间处理至少每 20 分钟续租一次：

```text
industry-chain topic renew --runner-id <runner_id> --node-id <node_id> --claim-token <claim_token>
```

### SubAgent 派发模板

每个 SubAgent 只处理不重叠的 `node_id` 范围，不预设来源、节点或企业。

```text
你负责 Runner {{runner_id}} 的 node_id {{node_id 或范围}}。先完整阅读 skills/researching-industry-chains/SKILL.md，领取或确认主题并保存有效 claim_token。

按 Skill 的四个终态门槛完成检索、来源扫描、节点还原和企业归属。先查看完整页面或完整图，只有局部文字、框线或连接关系不清时才裁切或放大，清楚区域不重复处理。

每个合格来源完整整理后一次性通过 industry-chain CLI 写入九字段 records。所有数据操作和终态操作携带有效 claim_token。搜索饱和后提交 completed、no_qualified_source 或 fail，并汇报 node_id、正式主题、终态、来源组数、数据行数、来源 URL 和交付 XLSX 路径。
```

## 单个主题流程

### 1. 确认主题

领取结果中的正式主题、`path` 和 `aliases` 是主题身份依据。`path` 只用于理解目录位置，不作为产业链节点。搜索词覆盖正式主题、批准别名、相关表达，以及产业链、产业图谱、全景图、企业布局、竞争格局、研究报告等限定词。

来源范围比正式主题宽或窄时可以保留，但在来源首行备注写明“范围变化”和具体差异。明显相邻但不是同一产业链的来源排除。图题、章节和正文指向同一产品或技术路线时按精确匹配处理；只有产业范围实际扩大或缩小时才标记范围变化。

来源优先级为政府或研究机构、证券研究、咨询机构、行业协会、专业数据库和白皮书。优先采用 2024 年及以后来源；较早来源在首行备注写“来源早于2024年”，日期无法确认时写“发布日期未识别”。

### 2. 判断产业链资格

一个来源只有同时满足以下条件才形成来源组：

1. 图、表或正文明确表达产业角色之间的连续关系，例如原材料或零部件 → 制造或服务 → 集成或运营 → 应用或客户；服务业可以使用不同名称，但必须存在清楚的提供方、承接方和需求方关系。
2. 至少一组企业能够通过来源内部证据直接对应一个已有节点。

标题含“产业链”“全链路”“生态图谱”或图中存在方框、箭头，本身不能证明产业链资格。以下内容单独出现时不合格：

- 工艺流程、业务流程、工作流和工作原理；
- 技术路线、系统架构和功能模块图；
- 产品结构、零部件清单和应用场景集合；
- 企业名单、相关标的表、排行榜、展商目录、区域热力图和没有角色关系的生态版图。

先判断图表达的语义，再读取节点和企业。未通过资格门槛时，不生成记录，不用其他企业图或正文名单补成产业链，也不调用 `dataset insert`。

### 3. 扫描完整来源

一个网页、报告或 PDF 独立形成一个来源组。同一底层文档的分页、正文、主产业链图、后续企业图表和明确正文可以综合；其他 URL 或其他报告的内容不得补入。同一底层文档的转载或托管版本只交付一组，优先保留原始发布地址；原址不可访问时选择内容最完整、图片最清晰的版本。

来源可以只覆盖产业链的一部分，但已展示的范围必须完整解析；与正式主题相比存在范围变化时按前述规则备注。

按以下顺序扫描，不边读边写：

1. **扫描**：检查标题、目录、图号、图题、正文引用、页码和网页分页，登记主产业链图、补充节点图、企业图表、明确正文和排除项。
2. **抽取**：先收集所有可读阶段、父节点、子节点、正文枚举项和企业组，不急于决定最终路径或归属。
3. **投影**：来源扫描结束后再还原产业链树、挂载企业并生成九字段行。

网页出现页码、`下一页` 或类似分页入口时，先确认总页数并逐页打开到最后一页。分页属于同一来源；未到最后一页不得提交来源终态。长篇 PDF 可以用目录、图表目录和文本搜索定位候选页，但所有用于节点或企业判断的图片页都必须实际查看。

先看完整页面或完整图。只有局部文字、框线、连接线或 Logo 无法可靠读取时，才裁切或放大对应区域；已经清楚的区域不重复处理。OCR、正文抓取、搜索摘要或图片下载成功不能替代视觉检查。

主产业链图无法读取时，先尝试原图地址、浏览器缩放、页面截图或 PDF 高分辨率渲染。正文只有在独立、明确地列出完整产业链结构和企业关系时，才能替代不可读图片；否则排除该来源，不以“部分可读”为由提交残缺主图。

### 4. 还原节点树

以来源中的框、分组标题、连接线、缩进、包含关系和阅读方向还原产业链树，不先建立标准产业链再套入原文。图片或表格优先；正文中“包括、分为、由……构成”等明确枚举可以补充图片未展示的节点。

每个可读节点都单独成行：

- 父节点本身也是节点，无论是否有企业都保留父节点行；
- 子节点不能用父节点行代替，多个并列节点分别成行；
- 无企业的节点仍保留，公司留空；
- 一个框表达组合节点时原样保留，表达多个并列节点时拆开；
- 省略号、示意占位符和装饰文字不生成节点。

节点名称、层级和顺序保持来源原义，不标准化、不润色、不补全。分类 1 至分类 4 必须连续；超过四级时，从第四级开始按原始顺序合并为 `第四级 > 第五级 > 第六级`，并在来源首行备注说明。

### 5. 挂载企业

企业归属按以下顺序判断：

1. 产业链图中的位置、连接、框或图例；
2. 企业表的标题、分组和字段；
3. 正文明示某企业生产、提供、运营或布局某个节点对应的产品或服务。

使用离企业名单最近的明确节点标题、表头或语义分组作为归属锚点。分号、分组标题或表格行已经区分企业组时，不得把相邻企业组合并到更宽的父节点。“主要上市公司、相关企业、代表公司、相关标的”等名单不能仅凭主题相关性挂载；只有同一来源另有明确节点关系时才使用。

企业只写在直接证据支持的最小节点行。证据只到父节点时只挂父节点，不向子节点继承；子节点照常保留且公司留空。同一路径的企业合并到一行，完全重复名称删除，按来源出现顺序用顿号连接。

不同企业证据发生冲突时，依次采用图中明确位置、分组表或企业列表、正文明确介绍；无法消解时不强行挂载，在来源首行备注说明。

优先使用来源内部确认的企业全称；只能确认品牌名或简称时保留原样，不用外部知识扩展或改写。无法确认归属的企业不写入公司字段，并在来源首行备注中写明“发现但无法归属：企业名称”；不得静默省略。

### 6. 覆盖检查

写入前在内存中逐项核对：

- 来源分页和相关页已经扫描到末尾；
- 每个接受的产业链图、表和明确正文都已处理；
- 每个可读节点都对应一条完整路径行；
- 每个可读企业组都已挂载，或已在首行备注说明无法归属；
- 没有把流程图、架构图、生态版图、热力图或无节点关系名单写成产业链；
- 没有把父节点企业继承给子节点，也没有把相邻企业组合并到过宽节点。

任何一项未完成，不得写入来源组或提交主题完成。

### 7. 写入来源组

来源完整解析后，在内存中整理固定九字段，不增加证据、置信度、搜索过程、截图或推理字段：

```json
{"records":[{
  "主题":"正式主题",
  "信源主体":"发布主体",
  "分类1":"上游",
  "分类2":"节点",
  "分类3":"",
  "分类4":"",
  "公司":"甲公司、乙公司",
  "信源URL":"https://example.com/report",
  "备注":"仅来源组第一行可填写"
}]}
```

九个字段全部是字符串。主题、信源主体、分类 1 和信源 URL 不能为空；分类不能断层；组内主题、信源主体和 URL 必须一致；只有第一行填写备注；来源组至少一行公司非空；信源 URL 必须是合法 HTTP(S) 地址。来源组内按原图或原文阅读顺序排列，父节点有独立行时放在其子节点行之前。

信源主体按发布关系填写：原始发布写原始主体；转载或托管写 `发布平台（原始主体）`；只能识别发布平台时写 `发布平台（原始主体未明）`。

一个来源的全部行一次性写入，不能边读边逐行提交。PowerShell 向原生命令传递中文时显式使用 UTF-8：

```powershell
$OutputEncoding = [System.Text.UTF8Encoding]::new($false)
$env:PYTHONIOENCODING = 'utf-8'
$payload = @'
{"records":[{"主题":"正式主题","信源主体":"发布主体","分类1":"上游","分类2":"节点","分类3":"","分类4":"","公司":"企业名称","信源URL":"https://example.com/report","备注":""}]}
'@
$payload | industry-chain dataset insert --runner-id <runner_id> --scope source_group --parent-id <node_id> --claim-token <claim_token> --input -
```

需要纠正时先用 `dataset get` 查看，再用 `dataset patch`、`dataset replace` 或 `dataset remove` 精确修改。XLSX 是交付投影，修改以 Runner JSON 为准。不要创建中间 JSON；截图、PDF、网页下载物、OCR 文件和日志只用于当前判断，不写入 Runner；Runner 目录只保留 `runner.json` 和交付 XLSX。

### 8. 搜索饱和与终态

每写入一个来源后继续搜索，不设置固定来源数量。一个完整轮次覆盖正式主题、批准别名和相关表达，并组合产业链、产业图谱、全景图、研究报告、企业布局和竞争格局等限定词。第二轮改变查询组合或来源入口，并按底层文档去重。连续两轮没有新增独立合格来源后，才算搜索饱和。

```text
industry-chain topic finish --runner-id <runner_id> --node-id <node_id> --claim-token <claim_token> --outcome completed
industry-chain topic finish --runner-id <runner_id> --node-id <node_id> --claim-token <claim_token> --outcome no_qualified_source
industry-chain topic fail --runner-id <runner_id> --node-id <node_id> --claim-token <claim_token> --code <错误代码> --message <简短说明>
```

`completed` 要求至少一个来源组；`no_qualified_source` 要求没有来源组。浏览器、网络、视觉能力或运行环境出现系统性异常时提交失败，不把异常主题视为完成。自动批次只领取 `pending` 主题；失败主题由明确补跑重新领取。

主题终态后汇报 node_id、正式主题、终态、来源组数量、数据行数、来源 URL 和交付 XLSX 路径；失败时补充原因。
