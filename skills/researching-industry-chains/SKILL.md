# 产业链来源检索与解析

## 适用条件

用于按主题批量寻找独立来源，把网页、PDF、图片和表格中的产业链节点及企业归属转换为九字段数据。运行环境必须同时具备：

- 互联网搜索能力；
- 可操作网页和 PDF 的浏览器；
- 页面截图或 PDF 高分辨率渲染能力；
- 能够实际查看截图内容的视觉能力；
- 已安装的 `industry-chain` CLI。

缺少搜索、浏览器或视觉能力时，不得用正文猜图。领取主题后发现能力不可用，应提交失败状态。

## 启动方式

所有 Runner 相关命令都必须显式传入 `--runner-id`。

新建批次：

```text
industry-chain runner create --name <任务名称> --config <topic_identity.yaml路径>
```

继续已有批次时先查看状态，再领取尚未尝试的主题：

```text
industry-chain runner status --runner-id <runner_id>
industry-chain topic claim-next --runner-id <runner_id>
```

指定补跑失败主题，或显式重开终态主题：

```text
industry-chain topic claim --runner-id <runner_id> --node-id <node_id>
industry-chain topic claim --runner-id <runner_id> --node-id <node_id> --reopen
```

领取响应中的 `claim_token`和`lease_expires_at`必须保存。处理 `in_progress`主题时，新增、修改、替换、删除来源以及提交结束或失败都要携带当前令牌。长时间检索时至少每20分钟续期一次：

```text
industry-chain topic renew --runner-id <runner_id> --node-id <node_id> --claim-token <claim_token>
```


## 单个主题的执行流程

### 1. 确认主题身份

领取结果会返回正式主题、`path`和`aliases`。`path`只帮助理解主题位置，不作为产业链节点。搜索词应覆盖正式主题、批准别名、相关表达和“产业链、产业图谱、全景图、企业布局、竞争格局、研究报告”等限定词。

更宽、更窄或限定词不同的产业链可以保留，但首行备注必须写明“范围变化”及具体差异。明显相邻但不是同一产业链的来源排除。

正式主题与图题存在明确的同义、近义或行业表达差异时，结合章节标题、图题、正文定义和节点内容判断是否指向同一对象。指向同一产品或技术路线时按精确匹配处理；只有明确扩大或缩小产业范围时才标记“范围变化”。

### 2. 判断来源是否合格

一个网页、报告或 PDF 只有同时满足以下条件才形成一组数据：

1. 存在可识别的产业链结构；
2. 至少有一组企业能够通过来源内部证据明确归属到已有节点。

写入前必须先通过产业链证据门禁：至少确认一张明确的产业链图、产业链表格，或正文中明确的上游/中游/下游等结构化节点。驱动/传动/感知等系统架构、技术路线、零部件清单和企业名单单独不算产业链证据；未通过门禁不得生成节点或企业记录，也不得调用 `dataset insert`。

产业链可以不完整。没有企业的其他图中节点仍须完整保留。只出现企业名单但不能对应任何节点，不满足企业归属条件。

同一来源可以综合使用该文档内的产业链图、后续企业图、企业列表、表格和正文；不得把其他 URL 或其他报告的节点、企业补入。不同来源分别形成来源组。同一底层文章或报告的转载、托管版本只交付一次，优先保留原始发布地址；原址不可访问时选择内容最完整、图片最清晰的地址。

来源优先顺序是政府机构、研究院、证券研报、咨询机构、行业协会、权威数据平台和企业白皮书。媒体、转载平台、文件站、自媒体或主体不明来源只要证据合格也可保留，但必须准确标注转载关系。

信源主体填写规则：原始主体直接发布时写原始主体；转载或托管时写`发布平台（原始主体）`；只能识别发布平台时写`发布平台（原始主体未明）`。详细转载说明只写该来源第一行备注。

优先采用2024年及之后的来源。更早来源合格时保留，并在首行备注写明“来源早于2024年”和可识别发布日期；无法识别日期时写“发布日期未识别”。

### 3. 扫描完整来源

找到第一张产业链图后不能停止。继续检查网页或报告的剩余部分，直到不再出现可归属的新节点或企业：

- 后续产业链补充图和分层图；
- 企业图、竞争格局图和重点企业图；
- 企业列表和表格；
- 明确描述产业链结构或企业业务关系的正文。

先根据目录、图号、图题、页面和正文引用建立本来源的图表清单，再逐项定位和检查。来源本身可以只展示部分产业链，但每一张已发现的图表中所有可识别的阶段、分类框和叶子框都必须完整解析。

长篇 PDF 可以先用目录、文本搜索和页码定位候选页。证券研报等页面必须用浏览器定位实际页码并截图。所有用于节点或企业判断的图片页，都必须截图或高分辨率渲染后使用视觉能力实际查看；OCR 文本、下载成功或网页摘要不能替代视觉检查。

先自动尝试原图下载、浏览器缩放、分页截图和 PDF 高分辨率渲染。仍无法确认时，只保留能够明确读取的内容，并在首行备注说明未解析范围。剩余证据仍满足来源资格时可部分交付，否则排除该来源并继续搜索，不暂停等待人工补图。

页面滚动检查或查看图片时，如果文字、Logo、框线、连接线或其他元素看不清，必须裁切并放大对应核心区域后再判断，不能根据模糊内容猜测节点或企业。

同一页面存在左右、上下或多栏图表时，每个图题对应的图块都是独立解析对象，必须分别截图、裁切、放大并读取，不能把整页看作一个已经完成的图表。图表清单中已发现但尚未定位、截图或可靠读取的图，不得提交该来源的最终数据。

### 4. 还原节点与企业

先根据原图中的框、标题、连接线、缩进、包含关系和阅读方向还原产业链树，再把树投影为数据行。每一行表示从根节点到某个节点的完整路径，以及直接归属于该路径终点节点的企业集合。不得先凭行业知识构建标准产业链，再把图片内容套入预设结构。

图题中出现“产业链构成”“产业链全景”“产业链图谱”或同类表达，且图中存在上游、中游、下游、阶段箭头或层级框时，按完整产业链主图解析，不得只提取一级标题或把它当作普通插图。

产业链结构的证据优先级为：图片或表格 > 正文中的明确结构化表述。正文只有明确表达“产业链上游包括……”“中游分为……”等层级关系时，才能补充图表未展示节点。普通产品介绍、业务描述和顺带提及的名词不能成为节点。

企业归属的证据优先级为：产业链图明确位置 > 企业列表 > 正文明确介绍。

企业列表的标题、分组或表格字段必须明确对应已有节点；正文必须明确表达某企业生产、提供或布局该节点对应的产品或服务。“相关企业、代表公司、行业参与者、上市公司”等无节点关系名单不得挂载。证据只支持父节点时，只挂父节点，不能下挂；父节点企业不能自动继承给子节点。冲突时高优先级证据优先，无法消解的企业从不确定节点排除，并在首行备注说明冲突。

节点名称和层级保持原图原义，不标准化、不润色、不补全。原图把“上游：基础设施层”作为整体标题时，分类1完整填写该标题。一个框表达多个独立叶子节点时拆成多行；表达组合名称时原样保留。省略号、示意占位符和装饰文字不作为节点。

每条独立节点路径单独一行。分类1至分类3保留前三层；原图超过四级时，从第四级开始按原始顺序合并到分类4，例如`第四级 > 第五级 > 第六级`，并在首行备注说明“原图层级超过4级，后续层级合并至分类4”。

企业只写在证据直接支持的节点行。企业只属于父节点时，额外保留父节点行并把企业写在那里；子节点行仍保留且公司留空。同一路径的企业在写入前合并，完全重复名称删除，按来源出现顺序用顿号`、`连接。优先使用来源内部明确出现的企业全称；来源内部只能确认品牌名或简称时保留原样，不用外部网站或模型知识扩展。

提交来源组前，逐项核对图表清单和原图中的阶段标题、分类框、叶子框与数据行；任何可读的独立框没有对应路径行时，不得提交来源终态。图表本身没有企业的节点仍须保留，公司留空；同一来源的其他图表或正文只能补充有直接证据的企业归属，不能把同页企业自动挂到所有子节点。

### 5. 形成来源组并写入

每个独立来源完整解析后，在内存中整理 CLI 所需的 `records` 数据，不增加证据、置信度、搜索过程、截图或推理字段。不要创建或保存中间 JSON 文件，数据只通过标准输入传给 CLI：

```text
{
  "records": [
    {
      "主题": "正式主题",
      "信源主体": "发布主体",
      "分类1": "上游",
      "分类2": "节点",
      "分类3": "",
      "分类4": "",
      "公司": "甲公司、乙公司",
      "信源URL": "https://example.com/report",
      "备注": "仅来源组第一行可填写"
    }
  ]
}
```

固定九字段全部是字符串。`主题、信源主体、分类1、信源URL`不能为空；分类层级不能中间断层；组内主题、信源主体和 URL 必须一致；只有第一行可写备注；来源组至少一行公司非空；URL 必须是合法 HTTP(S) 地址。组内行严格遵循原图或原文阅读顺序，通常从上到下、从左到右、从上游到下游，父节点企业行放在子节点前。

完整解析并汇总一个来源后，一次原子写入该来源的全部行：

Windows PowerShell 向原生命令传递中文时，必须显式使用 UTF-8；不要直接把中文 here-string 管道给 CLI，否则字段名可能乱码并被 Client 拒绝。

```powershell
$OutputEncoding = [System.Text.UTF8Encoding]::new($false)
$env:PYTHONIOENCODING = 'utf-8'
$payload = @'
{"records":[
  {
    "主题":"正式主题",
    "信源主体":"发布主体",
    "分类1":"上游",
    "分类2":"节点",
    "分类3":"",
    "分类4":"",
    "公司":"企业名称",
    "信源URL":"https://example.com/report",
    "备注":""
  }
]}
'@
$payload | industry-chain dataset insert --runner-id <runner_id> --scope source_group --parent-id <node_id> --claim-token <claim_token> --input -
```

成功响应会返回 `source_group_id`和每行 `row_id`。需要纠正时先用 `dataset get`查看，再使用 `dataset patch`、`dataset replace`或`dataset remove`精确修改。不要在来源尚未扫描完整时逐行写入。每次来源级写入成功后，Client 会原子保存状态并刷新 XLSX。

成功响应会返回 `source_group_id`和每行 `row_id`。需要纠正时先用 `dataset get`查看，在内存中修正 `records` 后再次通过标准输入提交，或使用 `dataset patch`、`dataset replace`和 `dataset remove`精确修改。不要创建来源 JSON 文件，不要运行 `python -m json.tool`检查中间文件，也不要在来源尚未扫描完整时逐行写入。每次来源级写入成功后，Client 会原子保存状态并刷新 XLSX。

截图、PDF、网页下载物、OCR 中间文件和其他证据材料只用于当前判断，不写入 Runner。Runner 目录只保留 `runner.json`和当前交付 XLSX，不创建`evidence`目录或其他证据文件。

### 6. 搜索饱和与终态

写入一个来源后继续搜索，不设置固定篇数。一个完整搜索轮次至少覆盖正式主题、全部批准别名、主题相关表达，并分别组合“产业链、产业图谱、全景图、研究报告、企业布局、竞争格局”等限定词；检查搜索结果的后续页或等价结果范围，并对发现的 URL 做底层文档去重。第二轮应改变查询组合或来源入口。连续两轮均无新增独立合格来源，才算搜索饱和。

已写入至少一个来源组时提交：

```text
industry-chain topic finish --runner-id <runner_id> --node-id <node_id> --claim-token <claim_token> --outcome completed
```

搜索饱和但没有合格来源时提交：

```text
industry-chain topic finish --runner-id <runner_id> --node-id <node_id> --claim-token <claim_token> --outcome no_qualified_source
```

浏览器、网络、视觉能力或运行环境出现系统性异常时提交失败，不把异常主题视为完成：

```text
industry-chain topic fail --runner-id <runner_id> --node-id <node_id> --claim-token <claim_token> --code <错误代码> --message <简短说明>
```

每个主题提交终态后立即简要汇报结果，至少包括 `node_id`、正式主题、终态、来源组数量、写入行数、来源 URL 和交付 XLSX 路径；失败主题补充失败原因。批量任务不必等全部主题结束后再统一汇报。

自动批次只持续使用 `topic claim-next`处理 `pending`主题。没有可领取的待处理主题后查看 Runner 状态并停止；失败主题留给明确指定的补跑，不在同一轮自动反复领取。

需要并行派发研究 Agent 时，先统计本次待处理主题的 `node_id` 数量，再据此决定并行 Agent 数量并尽量均分连续的 `node_id` 范围。每个派发任务必须明确负责的 `node_id` 范围；提示词只写任务目标、输入范围、必要约束和交付要求，不预设过细的浏览、搜索或解析动作。

## 快速检查

- 每个来源同时有产业链结构和至少一组明确企业归属。
- 不同 URL、不同报告不混合；同一底层文档不重复交付。
- 完整页面或报告已扫描，后续企业图没有遗漏。
- 已建立图表清单，复合页面的每个图块均已单独检查，所有可读阶段、分类框和叶子框均有对应路径行。
- 用作证据的图片页均已由视觉能力实际查看。
- 每个独立节点路径一行，企业只挂在直接证据支持的层级。
- 一个来源一次通过 CLI 标准输入提交完整 `records`，首行之外备注为空，不创建中间 JSON 文件。
- 搜索完成连续两个无新增轮次后才提交终态。
