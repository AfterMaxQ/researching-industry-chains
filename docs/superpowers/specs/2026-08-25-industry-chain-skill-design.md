# 产业链检索与解析 Skill 设计

## 1. 项目定义

项目位于 `E:\industry-chain-paeser-skills`，提供一套不绑定具体 Agent 的产业链检索、解析和交付能力。

项目接收外部主题配置，由 Agent 完成主题领取、公开资料搜索、来源筛选、浏览器操作、视觉读图、产业链还原和企业归属判断。Python Client 管理批次、主题状态、结构化数据、并发写入和 XLSX 交付。

项目不依赖 `E:\Industry-chain-parser-v3` 的代码、Skill、配置副本或运行环境。外部 `topic_identity.yaml` 只作为 Runner 创建时的只读输入。

项目不提供常驻服务、数据库、知识图谱、搜索爬虫或 Agent 专用 SDK。Agent 通过 CLI 和 JSON 调用 Client。

## 2. 业务目标

每个正式主题需要完成以下闭环：

1. 读取正式主题、主题路径和批准别名。
2. 搜索与主题相关的产业链资料。
3. 筛选包含产业链结构和企业归属证据的合格来源。
4. 完整检查网页、报告或 PDF 内的产业链图、后续企业图、表格和正文。
5. 使用视觉能力还原节点层级和企业位置。
6. 按固定九字段生成产业链数据行。
7. 通过 Client 按来源组原子写入。
8. 实时刷新 Runner 对应的 XLSX。
9. 搜索饱和后提交主题结果，继续处理下一个主题。

最终 XLSX 固定为以下九列：

1. 主题
2. 信源主体
3. 分类1
4. 分类2
5. 分类3
6. 分类4
7. 公司
8. 信源URL
9. 备注

## 3. 业务对象

### 3.1 Runner

Runner 表示一次独立运行批次。每个 Runner 拥有独立的主题目录快照、主题状态、来源组、数据行、内部 JSON 和交付 XLSX。

Runner 创建时接收：

- 模型指定的任务名称
- 外部 `topic_identity.yaml` 绝对路径

Runner ID 由系统时间、经过文件名安全处理的任务名称和短随机后缀组成。每个 Runner 使用独立目录：

```text
runs/
└── <runner_id>/
    ├── runner.json
    └── <runner_id>_交付数据.xlsx
```

### 3.2 主题

Runner 创建时读取外部 YAML，为每个主题保存：

- `node_id`
- 正式主题
- `path`
- `aliases`
- 配置顺序
- 当前状态
- 当前失败信息
- 当前领取信息
- 来源组

`node_id`按照配置顺序生成，例如 `node_0001`。Runner 后续只使用内部快照。外部 YAML 的修改不改变已有 Runner 的主题总数、编号、路径、别名和状态。

### 3.3 来源组

一个网页、一篇文章、一份报告或一个 PDF 构成一个独立来源组。同一文档内的图片、表格和正文可以相互补充，不同底层文档不得拼接成一条产业链。

来源组包含一个稳定的 `source_group_id`、原始顺序、创建时间、修改时间和一组数据行。

### 3.4 数据行

每行表示一条直接可证的产业链节点路径及其企业集合。数据行包含稳定的 `row_id`、原始顺序、创建时间、修改时间和固定九字段记录。

同一路径的多家企业写入同一个公司单元格，使用顿号分隔。不同叶子节点分别成行。父节点企业只保留在父节点行，不向子节点继承。

## 4. 跨 Agent 运行约束

项目只维护一份通用 `SKILL.md`，不提供 Codex、Trae 或其他 Agent 的专用适配文件。

Skill 使用能力描述，不写入具体插件名或工具名。运行环境必须提供：

- 网页搜索能力
- 交互式浏览器能力
- 页面截图能力
- 图片视觉理解能力
- 命令行调用能力

视觉能力缺失时不得开始产业链解析。动态网页、在线阅读器或 PDF 需要交互式定位但浏览器能力不可用时，当前主题进入 `failed`，不得静默降级为纯文本推断。

## 5. 主题配置

主题配置由调用方在 Runner 创建时传入。Client 读取 `themes` 下全部主题的正式名称、`path`和`aliases`，并按配置顺序建立 Runner 主题目录快照。

主题路径只用于语境理解、消歧和相关性判断，不得写入分类1至分类4。批准别名用于搜索扩展和精确匹配。

配置文件不存在、无法读取、主题结构无效时，Runner 创建失败。Client 不修改外部 YAML，不自动生成主题、路径或别名。

CLI 支持按正式主题读取配置，也支持按正式主题、别名或路径关键词模糊查询。Runner 创建后，模型可以通过 `node_id`查询该批次内的主题信息。

## 6. Runner 生命周期

主题状态包括：

- `pending`
- `in_progress`
- `completed`
- `no_qualified_source`
- `failed`

Runner 默认返回主题总数、各状态数量、剩余数量、当前处理主题列表、下一个待处理主题和失败主题列表。`remaining`等于 `pending + failed`。

主题通过原子领取进入 `in_progress`。一次自动批次只自动领取 `pending`主题，每个待处理主题尝试一次。全部 `pending`主题处理后批次结束，`failed`主题由补跑入口显式领取。

主题结束规则：

- 搜索饱和且至少写入一个有效来源组：`completed`
- 搜索饱和且没有合格来源：`no_qualified_source`
- 搜索、浏览器、视觉或运行环境发生系统性异常：`failed`

提交 `completed` 时主题必须至少有一个有效来源组。提交 `no_qualified_source` 时主题不得包含来源组。校验失败时主题保持 `in_progress`。

终态主题允许显式重开。重开 `completed`时保留已有数据，重开 `no_qualified_source`时从空数据状态继续处理。

### 6.1 领取令牌与租约

`topic claim-next`和`topic claim`返回 `claim_token`与 `lease_expires_at`。研究 Agent 向 `in_progress`主题新增来源、结束主题或提交失败时必须携带当前令牌。

令牌规则：

- 同一主题同时只有一个有效令牌。
- 每次携带有效令牌的写入、续期、结束或失败操作自动延长租约。
- 租约有效时其他 Agent不能领取该主题。
- 租约过期后可以重新领取，旧令牌立即失效。
- 默认租约时长为60分钟。
- Client 提供主题续期命令，Skill 在长时间浏览或读图期间至少每20分钟续期一次，并在来源组写入前再次续期。
- `claim-next`优先重新领取租约已过期的 `in_progress`主题，再按配置顺序领取 `pending`主题；租约仍有效的主题不会被重复返回。
- 审核 Agent可以直接修改终态主题。
- 审核 Agent修改 `in_progress`主题时必须提供当前有效令牌。

Runner 级文件锁保证文件一致性，领取令牌保证主题处理所有权。两者不能互相替代。

Runner 支持三种启动方式：

- 新建批次：创建 Runner 后自动处理全部 `pending`主题。
- 继续批次：处理租约已过期的 `in_progress`主题和尚未尝试的 `pending`主题。
- 指定补跑：通过 Runner ID和 node ID领取 `failed`主题，或者显式重开终态主题。

## 7. 搜索规则

搜索词由以下内容组合：

- 正式主题
- 批准别名
- 模型确认与主题确实相关的表达
- 产业链、产业链图、全景图、图谱、上下游、企业格局、PDF、研报等限定词

模型知识可以用于判断主题或别名之外的表达是否与正式主题相关，但不能用于新增节点、补充企业或推断企业归属。

搜索优先级包括政府机构、研究院、证券研报、咨询机构、行业协会、权威数据平台和企业白皮书。新闻媒体、转载平台、Medium、自媒体和主体不明文件不设硬性排除，只要满足合格来源标准即可使用。

同一底层文章或报告只交付一次。优先使用原始发布地址；原始地址不可访问时，使用内容完整、图片清晰的托管地址。不同年份、不同版本或内容存在实质差异的报告视为独立来源。

搜索采用信息增益停止：

1. 完成正式主题、别名和相关表达的基础查询。
2. 使用已发现资料中的专业术语扩展查询。
3. 连续两个完整搜索轮次没有新增合格来源。
4. 新结果主要为已处理 URL、重复转载或已判定不合格页面。

合格来源数量不设上限。运行超时或工具故障不等于搜索饱和。

## 8. 来源资格与隔离

同一来源必须同时满足：

1. 存在可识别的产业链结构。
2. 至少有一组企业能够明确归属到产业链节点。

产业链可以不完整。来源中所有能够确认的有效节点都需要保留，没有企业的节点行公司字段留空。

不同网页、报告或 PDF 分别形成来源组。不同来源之间禁止补节点、补企业或拼接层级。

主题匹配采用双轨规则：

- 正式主题或批准别名匹配属于精确匹配。
- 更宽、更窄、地域不同、应用场景不同或限定词不同的相关来源可以保留，第一行备注必须说明具体范围差异。
- 明显属于相邻行业但无法证明直接相关的来源排除。

优先使用2024年及之后的来源。2024年以前的合格来源可以保留，第一行备注写明来源早于2024年及可识别的发布日期。无法识别发布日期时写明发布日期未识别。

信源主体规则：

- 原始主体直接发布：填写原始主体。
- 转载或托管：填写 `发布平台（原始主体）`。
- 无法识别原始主体：填写 `发布平台（原始主体未明）`。
- 转载、托管和主体关系的补充说明只写在来源组第一行备注。

## 9. 来源完整扫描与视觉解析

找到第一张产业链图后不得立即结束来源解析。Agent 必须继续检查同一文档中的：

- 后续产业链补充图
- 企业图和企业列表
- 竞争格局图
- 产业链表格
- 图注
- 与节点或企业直接相关的正文

长篇 PDF 可以使用目录、文本搜索和页码定位候选页面。所有实际用于节点或企业归属的图片页必须截图并使用视觉能力查看。

视觉解析必须识别：

- 节点框
- 箭头和连线
- 包含关系
- 空间分区
- 阅读顺序
- 企业 Logo 所在位置
- 标题、图例和注释的作用范围

OCR、网页提取文本、图片说明和正文转录只能辅助定位和辨字，不能替代视觉判断。

图片模糊或页面受限时，依次尝试原图下载、浏览器缩放、PDF 高分辨率渲染、分页截图和其他可用视图。仍无法确认时只保留明确内容，并在第一行备注说明未解析范围。剩余内容仍满足来源资格时可以部分交付，否则来源不合格。

## 10. 产业链结构规则

结构证据优先级：

```text
图片或表格 > 正文中的明确结构化表述
```

图片或表格存在时，以其节点和层级为主。正文只有明确使用产业链上游、中游、下游、组成、分类或分支等结构化表述时，才能补充图表未展示的节点。普通产品介绍、业务描述或顺带提及的名词不能成为节点。

节点名称和层级必须保留来源原义：

- 不标准化
- 不润色
- 不补全
- 不使用行业知识重新命名
- 原图作为一个整体表达的标题不得擅自拆分
- 原图明确表示独立分支时分别成行
- 组合名称按原文保留
- 省略号、装饰文字、图例说明和占位符不作为节点

分类1至分类4按照来源真实层级填写。来源超过四级时，分类1至分类3保留前三层，从第四层开始使用 ` > `按原始顺序合并到分类4。第一行备注说明层级压缩。

## 11. 企业归属规则

企业归属证据优先级：

```text
产业链图明确位置 > 企业列表 > 正文明确介绍
```

企业列表的标题、分组或字段必须明确对应已有节点。正文必须明确表达企业生产、提供或布局节点对应的产品或服务。只有行业相关企业、代表企业、上市公司或参与者名单而没有节点对应关系时，不得挂载。

企业列表和正文只能向已有产业链节点补充企业，不能创造节点。证据只支持父节点时，企业只挂父节点，不得向子节点下挂。

来源内证据冲突时：

- 产业链图明确位置优先。
- 企业列表次之。
- 正文再次之。
- 低优先级证据可以在不冲突时补充或细化归属。
- 无法消解的企业从争议节点中排除，并在第一行备注说明冲突。

企业名称优先使用同一来源明确提供的全称。Logo、品牌名或简称可以结合同一来源的企业列表、图注和正文确认。来源内部无法确认时保留可识别的品牌名或简称，不使用其他 URL 或模型知识扩展全称。

同一来源、同一路径的企业由模型汇总到一行，删除完全重复名称，保持来源出现顺序，使用顿号连接。简称与全称只有在来源明确证明为同一主体时才合并。

## 12. 数据行规则

每个独立节点路径对应一行：

- 兄弟节点分别输出。
- 不同叶子节点不得合并。
- 父节点有独立企业时保留父节点行。
- 子节点没有企业时仍保留，公司字段为空字符串。
- 父节点企业不得继承到子节点。
- 同一路径企业不得按公司拆行。

来源组内部遵循原图或原文的阅读顺序，通常为从上到下、从左到右、从上游到下游。父节点企业行位于其子节点之前。

来源组按成功解析并写入的先后顺序获得 Runner 全局顺序。并发处理不同主题时，XLSX 仍按来源组实际提交顺序追加，不按主题或节点名称重新排序。修改时保留其他来源组和数据行的相对顺序。

每行重复填写主题、信源主体和原始 URL。只有来源组第一行可以填写备注，其余行备注为空字符串。

第一行备注可以包含：

- 主题范围变化及具体差异
- 来源早于2024年和发布日期
- 发布日期未识别
- 转载或托管关系
- 超过四级后的层级压缩
- 无法消解的企业证据冲突
- 部分图片或页面无法解析的范围

备注由模型生成，Client 不生成业务备注。

## 13. 模型 JSON 契约

模型按来源组一次性输出：

```json
{
  "records": [
    {
      "主题": "",
      "信源主体": "",
      "分类1": "",
      "分类2": "",
      "分类3": "",
      "分类4": "",
      "公司": "",
      "信源URL": "",
      "备注": ""
    }
  ]
}
```

模型输出不包含内部 ID、时间、证据、置信度、搜索状态、处理状态或其他字段。空分类、空公司和空备注使用空字符串，不使用 `null`。

模型结构化输出 Schema 只保留 `records`数组和九字段记录：

```json
{
  "type": "object",
  "additionalProperties": false,
  "required": ["records"],
  "properties": {
    "records": {
      "type": "array",
      "minItems": 1,
      "items": {
        "type": "object",
        "additionalProperties": false,
        "required": [
          "主题",
          "信源主体",
          "分类1",
          "分类2",
          "分类3",
          "分类4",
          "公司",
          "信源URL",
          "备注"
        ],
        "properties": {
          "主题": {"type": "string"},
          "信源主体": {"type": "string"},
          "分类1": {"type": "string"},
          "分类2": {"type": "string"},
          "分类3": {"type": "string"},
          "分类4": {"type": "string"},
          "公司": {"type": "string"},
          "信源URL": {"type": "string"},
          "备注": {"type": "string"}
        }
      }
    }
  }
}
```

## 14. Client 职责

Client 负责：

- 主题配置读取和查询
- Runner 创建、列表、状态和导出
- 主题目录快照
- node ID、来源组 ID和数据行 ID
- 主题领取、令牌、租约和状态转换
- 九字段 Schema 校验
- 来源组跨行确定性校验
- 指定位置插入
- 行、来源组和主题粒度的读取、修改、替换和删除
- Runner 文件锁
- JSON 原子持久化
- XLSX 生成和 URL 超链接

Client 不负责：

- 搜索来源
- 判断来源是否合格
- 判断主题是否相关
- 解析产业链节点
- 判断企业归属
- 生成业务备注
- 合并跨来源证据
- 根据行业知识补节点或企业

## 15. Client 校验

来源组写入时执行以下确定性校验：

- 固定九个字段
- 所有字段为字符串
- 不允许额外字段
- 主题、信源主体、分类1和信源URL非空
- 分类层级不得中间断层
- 同一来源组的主题、信源主体和URL一致
- 只有第一行可以填写备注
- 来源组至少一行公司非空
- URL能够生成 HTTP 或 HTTPS 超链接

任意一行失败时整组拒绝。Agent 最多进行两次结构修正，仍不合法时不得写入部分来源组。

## 16. 内部状态

`runner.json`保存当前有效状态，不保存历史版本。核心结构为：

```json
{
  "runner_id": "",
  "name": "",
  "topic_identity_path": "",
  "created_at": "",
  "updated_at": "",
  "topics": [
    {
      "node_id": "node_0001",
      "主题": "",
      "path": [],
      "aliases": [],
      "order": 1,
      "status": "pending",
      "last_error": null,
      "claim": null,
      "source_groups": []
    }
  ]
}
```

来源组保存稳定 ID、Runner 全局顺序、首次写入时间、最后修改时间和数据行。数据行保存稳定 ID、组内顺序、首次写入时间、最后修改时间和当前九字段记录。主题、信源主体和 URL 不在业务记录外重复保存。

状态文件不保存模型推理、搜索过程、截图、证据文本、置信度和数据修改历史。

所有时间使用带时区的 ISO 8601 格式。

## 17. CLI 契约

CLI 命令名为 `industry-chain`。成功响应：

```json
{"ok": true, "data": {}}
```

失败响应使用非零退出码：

```json
{
  "ok": false,
  "error": {
    "code": "ERROR_CODE",
    "message": "简短错误信息"
  }
}
```

标准输出只包含 JSON。日志和调试堆栈写入标准错误。

### 17.1 主题身份

## 18. 数据操作语义

### 18.1 Get

读取主题、来源组或数据行的当前一致快照，不修改状态。

### 18.2 Insert

- 插入主题时生成新 `node_id`，初始状态为 `pending`。
- 插入来源组时接收完整 `records`数组并生成来源组 ID和数据行 ID。
- 插入数据行时接收完整九字段记录。
- 插入主题只修改当前 Runner 的内部主题目录，不修改外部 YAML。Runner 的主题总数和配置顺序在插入后重新计算。
- 未指定位置时追加到同级末尾。
- 指定 `before_id`或 `after_id`时在同级精确插入。

### 18.3 Patch

- 行级 Patch 可以修改任意九字段。
- 来源组 Patch 只允许批量修改主题、信源主体、信源URL和第一行备注。
- 主题 Patch 可以修改正式主题、`path`和`aliases`。正式主题变化时同步更新该主题全部业务行。
- Patch 保留目标 ID、创建时间和位置，只更新修改时间。

### 18.4 Replace

- 替换行时保留行 ID和位置。
- 替换来源组时保留来源组 ID和位置，旧行移除，新行获得新 ID。
- 替换主题时保留 node ID、位置和工作流状态，来源组与数据行整体重建。新来源组从该主题原有来源组的最早全局位置开始写入，其他主题来源组的相对顺序不变。
- 替换先完成全部校验，再原子提交。

### 18.5 Remove

- 删除行后来源组必须至少保留一行；删除最后一行时删除整个来源组。
- 删除来源组后保留其他来源组的相对顺序。
- 删除主题时同时删除其全部来源组。
- `completed`主题不得被修改为零来源组。
- `no_qualified_source`主题不得直接新增来源组。
- 破坏终态数据一致性的操作必须先重开主题。

普通审核修正不破坏终态与数据一致性时可以直接修改终态主题。修改 `in_progress`主题必须携带当前有效领取令牌。

## 19. 存储、并发和 XLSX

每个 Runner 使用独立文件锁。主题领取、状态变更、续期和所有数据修改均在锁内执行。

写入流程：

1. 获取 Runner 锁。
2. 读取并校验当前 `runner.json`。
3. 校验目标 ID、令牌、租约和位置。
4. 在内存中应用操作。
5. 执行 Schema 和跨行校验。
6. 生成临时 JSON 和临时 XLSX。
7. 替换正式文件；失败时恢复操作前状态。
8. 释放锁。

进程异常后以 `runner.json`为状态来源，`runner export`根据当前 JSON 重建 XLSX。Client 不根据 XLSX 反向生成内部状态。

XLSX 契约：

- 工作表名称为 `交付数据`
- 表头严格为固定九字段
- 不包含内部 ID、状态或时间
- 数据顺序与 Runner 当前状态一致
- 每个非空 URL 单元格设置可点击超链接
- 每次成功修改后实时刷新

## 20. 错误处理

配置、Schema、目标 ID、令牌、租约、状态、锁、JSON 和 XLSX 错误使用稳定错误代码。

主要错误边界：

- 配置无效时不创建 Runner。
- 模型来源组无效时整组拒绝。
- 单个候选页面失效时跳过该候选并继续搜索。
- 搜索、浏览器、截图或视觉能力整体不可用时主题失败。
- Runner 锁超时时不绕过锁写入。
- XLSX 被占用时返回 `XLSX_LOCKED`，不提交新的 Runner 状态。
- Runner JSON 损坏时返回 `RUNNER_STATE_INVALID`，不根据 XLSX 猜测恢复。
- 过期令牌写入返回明确错误，不修改数据。

临时文件不作为正式状态。下次操作可以清理遗留临时文件。

## 21. 项目模块

Python 包按职责划分：

- `cli.py`：命令解析、标准输入输出和退出码
- `identity.py`：YAML 读取、主题查询和快照构建
- `runner.py`：Runner 生命周期、主题状态、领取令牌和租约
- `dataset.py`：三个作用域的读取和数据操作
- `storage.py`：文件锁、原子持久化和恢复
- `excel.py`：九列 XLSX 和超链接
- `errors.py`：稳定错误代码

运行依赖包括 Python 3.11+、PyYAML、jsonschema、openpyxl 和 filelock。模型 Schema 单独存放在 `schemas/record.schema.json`。测试覆盖配置、Runner、状态、租约、数据操作、并发、故障和 XLSX。

## 23. 测试与验收

单元测试覆盖：

- YAML 读取和模糊查询
- Runner ID和批次隔离
- 主题快照和 node ID
- 状态转换、终态重开和结束校验

- ID、顺序和时间字段

XLSX 测试覆盖：

- 固定工作表和九列表头
- URL 超链接
- 中文、英文、顿号和长文本
- JSON 与 XLSX 的顺序和内容一致
- 修改、替换、删除和手动重建

并发与故障测试覆盖：

- 多进程不会领取同一主题
- 有效租约不能被其他 Agent覆盖
- 过期租约可以安全重新领取
- 多进程写入不会覆盖 Runner 数据
- 锁超时、文件占用和临时文件失败不产生半次提交

Skill 场景验收覆盖：

- 静态网页产业链图
- 后续企业图
- 普通 PDF
- 需要浏览器翻页和截图的在线 PDF
- 图片结构与正文企业补充
- 企业证据冲突
- 超过四级的路径
- 2024年以前的来源
- 范围变化来源
- 重复转载来源
- 部分图片无法识别
- 没有合格来源
- 浏览器或视觉能力不可用

验收时必须确认 Agent 实际查看图片，单个来源完整扫描后一次性写入，主题结束状态与 Runner 数据一致。最终 XLSX 可以直接用于产业链交付审核。
